# Initiative Engine

Отдельная подсистема NeuroMita, которая даёт персонажу **самостоятельное поведение**:
наблюдение за окружением, формирование намерений и принятие решений о том, когда
заговорить, действовать или промолчать. Минимально вмешивается в существующий код
NeuroMita и использует его инфраструктуру: `ChatAPI`, `ToolManager`, `Memory/RAG`,
`MCP`.

## Что умеет сейчас

Движок реализует полный цикл «наблюдение → понимание → мотив → решение → действие →
обратная связь» на детерминированных эвристиках (без LLM на этапе решения).

**Наблюдение (Observation).**
- Подписка на события EventBus: `SEND_MESSAGE`, `ON_SUCCESSFUL_RESPONSE`,
  `ON_TOOL_DONE`.
- Дедупликация и фильтрация шумовых/технических событий (`EventProcessor`).
- Опрос активного окна через MCP (`get_active_window`) по расписанию.
- Нормализация источника события (`observation/source.py`, `EventSource`):
  `player` / `system` / `initiative` / `tool` / `external` / `unknown`. Определяется
  только по достоверным метаданным (`sender`, `event_type`, `task_uid`), никогда по
  тексту. `sender="System"` не считается инициативой; неизвестный источник не
  классифицируется как сообщение пользователя. Эмиттеры не изменяются.

**Восприятие (Perception).**
- Собирает персонаж, его личность (из промптов), Working State и релевантные
  воспоминания в структурированное «понимание ситуации».
- Обогащает события источником и значимостью; выделяет текущую тему (topic),
  открытые вопросы/фокусы (open_loops), даёт сводку (summary) и пересчитанную
  уверенность (confidence). Лёгкие детерминированные эвристики без LLM.

**Мотивация (Motivation).**
- Генерирует мотивы: «реагировать на событие», «продолжить незакрытый фокус»,
  «прокомментировать окно».

**Решение (Decision).**
- Детерминированная эвристика без LLM:
  - `initiate_dialogue` — начать разговор;
  - `act` — выполнить действие/инструмент;
  - `silence` — промолчать;
  - `defer` — отложить (лимит инициатив).
- Продолжение темы по последнему сообщению игрока после реального молчания.

**Действия (Actions).**
- Начало диалога через `ChatAPI.initiate()`;
- Инструменты через `ToolManager`/MCP с контролем прав (`PermissionPolicy`);
- Уважение `character_generation_lock` (не конкурирует с активным диалогом).

**Обратная связь (Feedback).**
- Оценка результата действия (успех/провал/неактуальность) и корректировка
  намерений (повысить/понизить приоритет, завершить).

**Намерения (Intentions).**
- Долгосрочные намерения в RAM + SQLite (`initiative_intentions.db`), восстановление
  при перезапуске, prune истёкших.

**Внутреннее состояние (Internal State).**
- Считывает реальные числовые переменные персонажа (`attitude`, `boredom`,
  `stress`) через `character.get_stats_dict()`, нормализует в [0,1] и добавляет
  производный индекс любопытства (curiosity). Показывается в мониторинге;
  доступно мотивам (Этап 5).

**Жизненный цикл и конфиг.**
- Гибридный планировщик: периодический тик + немедленная оценка по событию.
- Live-применение конфигурации без перезапуска, мгновенный старт из Песочницы.
- Статистика и мониторинг в отдельном окне; логирование по тумблеру.

## Конфигурация

Базовые поля `InitiativeConfig` (подробнее — в `config.py`):

| Поле | По умолчанию | Описание |
|---|---|---|
| `enabled` | `False` | Движок выключен по умолчанию |
| `scheduler_interval_sec` | `60.0` | Период принятия решений (сек) |
| `autonomy_level` | `"off"` | `off` / `subtle` / `full` |
| `max_actions_per_minute` | `1` | Лимит инициатив в минуту |
| `min_motive_priority` | `2` | Минимальный приоритет мотива для намерения |
| `filter_events` | `True` | Спам-защита / фильтрация событий |
| `respect_busy_character` | `True` | Не стартовать, пока персонаж генерирует |
| `enable_logging` | `False` | Подробное логирование цикла |
| `allow_initiate_dialogue` | `True` | Разрешить `ChatAPI.initiate()` |
| `observe_dialogue` / `observe_windows` | `True` | Источники наблюдений |
| `use_vision` | `False` | Использовать screenshot (vision) |
| `enabled_characters` | `[]` | Белый список персонажей (пусто = все) |

Настройки редактируются в **Песочнице** (панель «Инициатива») и сохраняются в
`settings`; применяются на лету.

## Защита от зацикливания

- **Лимит инициатив** (решения/минту).
- **Фильтр шума**: `send_message`, `on_successful_response` и технические события
  не являются мгновенными триггерами инициативы.
- **Дедупликация решений**: повторяющиеся решения подавляются по ключу
  `персонаж|действие|причина` с cooldown'ом.
- **Продолжение темы** — только после реального молчания (игрока и персонажа) и
  один раз на сообщение.
- **Действия не конкурируют** с активным диалогом (`character_generation_lock`,
  `respect_busy_character`).
- **Initiative Gate** (Этап 3) проверяет допустимость инициативы по состоянию
  пользователя: запрещает диалог при «не беспокоить», занятости, уходе спать и
  после прощания.

## Разделение источников и циклов (Этап 1)

Реализовано в коммите `db25f572` (ветка `release-patched`). Принцип: штатная система
диалога остаётся единственным владельцем ответов на явные обращения; Initiative Engine
наблюдает и формирует собственные мотивы, не дублируя ответы и не реагируя на свои
результаты.

- **Нормализация источника** — `observation/source.py`. `normalize_source()` относит
  событие к категории `EventSource` по достоверным метаданным. Эмиттеры не изменяются;
  категория добавляется в `event["source"]` в слое наблюдения.
- **`SEND_MESSAGE`** — источник контекста, не триггер инициативы. Значение `source`
  сохраняется в `_last_user_message`.
- **`ON_SUCCESSFUL_RESPONSE`** — обновляет `_last_assistant_ts` (активность) для любых
  ответов (обычных/инициативных/системных); триггером не является.
- **Защита от конкуренции** — в `_execute_decision` добавлена повторная проверка
  `respect_busy_character` перед `initiate_dialogue`/`act`: при занятости действие
  откладывается, штатный ответ не блокируется.
- **Собственные инициативы** — фиксируются в `_in_flight_initiative`
  (char_id → ts) в момент успешного `initiate_dialogue`, что позволяет коррелировать
  последующие ответы без правки `model_controller`.

Тесты: `src/utils/Testing/test_observation_source_normalize.py` (9),
`src/utils/Testing/test_engine_defense.py` (6).

## Интеграция с приложением

- Инициализация: `MainController` (регистрация `InitiativeEngine` в сервисах, сборка
  `InitiativeConfig` из настроек).
- Управление: Песочница → панель «Инициатива» (тумблеры, спинбоксы, мониторинг,
  логирование).
- Мониторинг: `initiative_monitor_dialog.py` — показывает статус/конфиг, анализ
  (perception + события), мотивы, решения, исполненные действия, намерения,
  числовое внутреннее состояние (любопытство и т.п.) и инициативы в полёте.
  Источник данных — расширенный `engine.stats()`.
- UI-обновления из фоновых потоков — через Qt-сигналы (без зависаний).

## Известные ограничения

- **Решение — эвристическое, без LLM.** DecisionEngine возвращает предсказуемые
  действия; нет «творческой» оценки мотивов моделью.
- **Unity-доставка инициативы не реализована.** Движок отправляет сообщения в
  десктоп-чат. Для вывода в запущенную игру нужна поддержка на стороне мода
  (Unity сама создаёт задачу по своему запросу; внешняя задача ей неизвестна).
- **Восприятие пока базовое**: личность берётся из первой строки промпта, память —
  одним блоком (1500 символов). Нет глубокого семантического анализа.
- **Vision (`use_vision`) выключен** по умолчанию и не подключён к реальному
  скриншоту.

# Дальнейшее развитие

> Ниже — видение стратегии развития Initiative Engine. Разделы «Что умеет сейчас»
> и «Дальнейшее развитие» соотносятся как **текущее состояние** и **целевая
> архитектура**. Не всё из развития уже реализовано.

## 1. Главная цель

Initiative Engine должен превратить NeuroMita из обычного реактивного собеседника в
самостоятельного персонажа, способного проявлять инициативу, формировать собственные
мотивы, принимать решения и самостоятельно взаимодействовать с пользователем.

При этом в NeuroMita уже существует штатная система обработки сообщений пользователя
и генерации ответов. Она отвечает на явные обращения пользователя, и её работу
необходимо сохранить.

**Initiative Engine не должен дублировать штатную систему диалога.**

Его задача — обеспечить поведение, которое выходит за рамки обычного ответа на
сообщение пользователя.

Примеры:
- самостоятельно начать разговор после продолжительного перерыва;
- вернуться к теме, которую персонаж хотел обсудить позднее;
- поделиться собственными наблюдениями;
- задать вопрос без предварительного обращения пользователя;
- проявить интерес к происходящему;
- самостоятельно выполнить разрешённое действие;
- продолжить собственную деятельность и сообщить о результате в подходящий момент.

Главный ориентир — естественность и самостоятельность поведения, а не количество
инициативных сообщений.

## 2. Критически важное разделение: обычный диалог и автономная инициатива

Это основной архитектурный принцип дальнейшей разработки.

### 2.1. Штатная система диалога

Существующая система NeuroMita отвечает за обычное взаимодействие:

```text
Пользователь отправляет сообщение
          ↓
Штатная система диалога
          ↓
Обработка сообщения
          ↓
Генерация ответа
          ↓
Отправка ответа пользователю
```

Это уже работающая функциональность программы.

Initiative Engine не должен:
- генерировать второй ответ на то же сообщение;
- самостоятельно повторять ответ штатной системы;
- запускать `ChatAPI.initiate()` как реакцию на обычный ответ персонажа;
- считать каждое сообщение пользователя поводом для отдельной инициативы;
- воспринимать собственные сообщения как новые внешние события;
- вмешиваться в активную генерацию.

### 2.2. Initiative Engine

Initiative Engine отвечает за самостоятельное поведение персонажа:

```text
       Внешние события и состояние
                   ↓
          Initiative Engine
                   ↓
              Perception
                   ↓
              Motivation
                   ↓
               Decision
                   ↓
         Ожидание / действие
                   ↓
          Initiative Action
                   ↓
        Результат и Feedback
```

Движок может наблюдать за обычным диалогом, использовать его содержание и обновлять
собственное понимание ситуации.

Но наблюдение за диалогом не означает необходимость отвечать на него.

**Получение информации и принятие решения о самостоятельном действии — два разных
процесса.**

### 2.3. Правила обработки событий диалога

Необходимо пересмотреть обработку событий EventBus и определить назначение каждого
события.

| Событие | Поведение Initiative Engine |
|---|---|
| Сообщение пользователя | Получить контекст, обновить восприятие и состояние. Не создавать второй ответ |
| Обычный ответ NeuroMita | Обновить контекст диалога. Не реагировать инициативным сообщением |
| Инициативное сообщение NeuroMita | Зарегистрировать собственное действие. Не воспринимать его как внешнее событие |
| Результат выполнения инструмента | Обработать результат в рамках текущего действия |
| Внешнее событие | Оценить, может ли оно стать поводом для самостоятельной инициативы |
| Периодический тик | Оценить состояние, мотивы и намерения независимо от поступления нового сообщения |

Точные названия событий и их семантику необходимо проверить по исходному коду.
Таблица описывает ожидаемое поведение, а не утверждает, что существующие события уже
полностью соответствуют этому разделению. **Статус на Этап 1:** первые четыре строки
(сообщение пользователя → контекст; ответ → активность; инициативное сообщение →
собственное действие; результат инструмента → обработка) уже реализованы в коде
(см. раздел «Разделение источников и циклов»).

### 2.4. Защита от повторной реакции и зацикливания

Необходимо реализовать или проверить следующие механизмы:

**A. Разделение источников событий.** Движок должен отличать: сообщения пользователя,
обычные ответы персонажа, инициативные сообщения, результаты собственных действий,
внешние и системные события. Если существующая система поддерживает метаданные
источника или идентификаторы запросов — использовать их. Не полагаться только на текст
сообщения для определения его происхождения.

**B. Привязка к циклу диалога.** Определить границы одного пользовательского обращения
и соответствующего ему ответа. Для одного обращения штатная система является
единственным владельцем генерации ответа. Initiative Engine может наблюдать за циклом,
но не должен создавать параллельную генерацию.

**C. Защита от самореакции.** Результаты собственных инициативных действий не должны
повторно запускать ту же цепочку принятия решений. Если движок сам отправил сообщение,
событие о его отправке учитывается как результат собственного действия, а не как новая
внешняя причина.

**D. Разделение наблюдения и запуска.** Событие может обновлять Perception, Working
State или контекст, не запуская немедленное действие. Необходимо разделить: получение
события, обновление состояния, формирование мотивов, принятие решения, выполнение
действия. Сам факт нового события не должен автоматически означать необходимость нового
сообщения.

**E. Защита от повторных генераций.** Использовать подходящие механизмы:
`character_generation_lock`, идентификаторы обращения/действий, дедупликацию событий,
cooldown, проверку активного диалога, контроль повторного выполнения действия.
Конкретная реализация должна соответствовать существующей архитектуре NeuroMita.

## 3. Архитектурные принципы

### 3.1. Повторное использование существующих систем

Перед добавлением новой функциональности исследовать существующие механизмы NeuroMita:

| Система | Ответственность |
|---|---|
| `MemoryManager` | Долговременная память |
| `RAGManager` | Поиск релевантных воспоминаний |
| `WorkingStateManager` | Текущее состояние и контекст |
| `HistoryController` | История диалога |
| `ActionMemory` | Память о действиях |
| Система эмоций | Эмоциональное состояние |
| Система скуки | Существующий расчёт скуки |
| `ChatAPI.initiate()` | Самостоятельное начало диалога |
| `ToolManager` / MCP | Выполнение инструментов |
| `character_generation_lock` | Защита от конфликтующих генераций |
| Screenshot MCP | Получение изображения экрана |

Это перечень существующих или ранее обнаруженных компонентов, интерфейсы и актуальные
возможности которых необходимо проверить по коду. **Не создавать параллельные системы**
памяти, истории, эмоций, скуки или инструментов без обоснованной необходимости.

### 3.2. Разделение состояний

Не смешивать:

- **Working State** — что происходит сейчас.
- **Intention** — чего персонаж хочет добиться в будущем.
- **Memory** — что персонаж помнит из прошлого.

Пример:

```text
Working State:
Пользователь рассказал о новой игре.
Сейчас обсуждается её механика.

Intention:
Позже спросить, удалось ли попробовать игру.

Memory:
Пользователь раньше интересовался похожими играми.
```

### 3.3. Независимость от обычного диалога

Initiative Engine должен работать параллельно со штатной системой общения, но не
конкурировать с ней за управление текущим диалогом.

Он может: наблюдать, анализировать, формировать мотивы, создавать намерения,
планировать, выполнять разрешённые самостоятельные действия, ждать подходящего момента.

Он не должен: отвечать вместо штатной системы, дублировать её ответы, вмешиваться в
активную генерацию, реагировать на собственные сообщения, бесконечно продолжать диалог
с самим собой.

## 4. Техническое задание: Этап 0. Аудит текущей реализации

**Приоритет: критический. Первый этап перед любыми изменениями кода.**

**Цель:** проверить, как Initiative Engine взаимодействует со штатной системой диалога,
и найти причины повторной реакции и возможного зацикливания.

**A. Исследовать штатную систему диалога:** как обрабатывается сообщение, где
запускается генерация, какие события возникают при получении и завершении ответа, как
определяется завершение обращения, как работает `ChatAPI.initiate()`, как используется
`character_generation_lock`.

**B. Исследовать Observation:** на какие события подписан движок, какие приходят при
обычном сообщении/ответе, может ли он отличить пользовательское сообщение от сообщения
персонажа, определить источник собственного действия, как обрабатываются повторные
события, какие запускают немедленный тик.

**C. Исследовать Decision:** может ли обычное сообщение привести к `initiate_dialogue`,
может ли завершение ответа привести к новой инициативе, может ли собственное сообщение
повторно запустить Decision, может ли одно обращение вызвать несколько инициатив, как
работают cooldown и активная генерация.

**D. Исследовать Actions и Feedback:** как отслеживается источник инициативного
сообщения, как определяется выполнение действия, как результат возвращается в
Observation, может ли Feedback повторно инициировать то же действие, есть ли защита от
повторного исполнения.

**E. Проверить сценарии зацикливания:**

1. **Обычное сообщение** — «Привет!» → штатный ответ. Движок наблюдает и обновляет
   контекст, второй ответ не создаётся.
2. **Продолжение разговора** — «Расскажи подробнее» → подробный ответ. Движок не
   создаёт дополнительный ответ.
3. **Собственная инициатива** — движок сам начинает разговор; событие об отправке
   регистрируется как собственное действие, а не как новое обращение.
4. **Активная генерация** — пользователь отправил сообщение, штатная система
   генерирует; никакой конкурирующей генерации.
5. **Повторное событие** — одно событие поступает несколько раз; не создаёт несколько
   одинаковых инициатив.

**Формат отчёта** по каждой проблеме:

```text
Проблема:
Текущая логика:
Файл / класс / метод:
Причина:
Ожидаемое поведение:
Минимальное исправление:
Затрагиваемые компоненты:
Тестирование:
```

Отдельно предоставить: схему штатного цикла диалога, схему цикла Initiative Engine,
точки пересечения, причины повторной реакции, предложение по разделению ответственности,
список уже существующих механизмов.

**На этапе аудита запрещено изменять код. Сначала предоставить отчёт и дождаться
согласования.**

## 5. Roadmap развития

### Этап 1. Разделение обычного диалога и автономной инициативы ✅ (реализован)

**Цель: полностью устранить дублирование и самореакцию.**

Задачи: разделить события обычного диалога и автономных действий; определять источник
каждого события; не запускать инициативную генерацию на обычное сообщение; не
реагировать на обычный ответ; исключить повторную обработку собственных инициатив;
сохранять наблюдение и обновление контекста; обеспечить независимость периодического
планировщика; проверить блокировку конкурентных генераций; добавить тесты на сценарии
этапа 0.

Реализация (коммит `db25f572`): нормализация источника в `observation/source.py`,
защитная проверка занятости в `_execute_decision`, маркер `_in_flight_initiative`,
поле `source` в контексте. Тесты: `test_observation_source_normalize.py`,
`test_engine_defense.py`.

**Критерий готовности:** обычный диалог работает как прежде, а Initiative Engine не
дублирует ответы и не зацикливается.

### Этап 2. Улучшение Perception ✅ (реализован)

**Цель: лучше понимать происходящее, а не просто регистрировать события.**

Задачи: анализировать содержание диалога; определять текущую тему; выделять важные
детали; определять незакрытые вопросы; использовать Working State и существующий RAG;
учитывать личность; различать важные события и шум.

Реализация: обогащение событий (source/significance), выделение `topic`,
детекция `open_loops`, сводка `summary`, пересчёт `confidence`. Лёгкие
детерминированные эвристики без LLM. Тесты: `test_perception_engine.py` (5).

**Критерий готовности:** движок понимает ситуацию и её историю, не создавая
автоматически ответ на каждое событие.

### Этап 3. User Interaction State и Initiative Gate ✅ (реализован)

**Цель: учитывать доступность пользователя для самостоятельного взаимодействия.**

Определять: активный разговор, временное отсутствие, завершение разговора, прощание,
намерение пойти спать, занятость, просьбу не беспокоить, возвращение. Различать
«Пока», «Я пошёл спать», «Сейчас занят», «Не отвлекай меня», «Я вернулся». Initiative
Gate должен проверять допустимость инициативы, а не формировать её.

Реализация: `interaction/user_interaction_state.py` (детекция сигналов
goodbye/sleep/busy/do_not_disturb/return + активный разговор),
`interaction/initiative_gate.py` (блокировка `initiate_dialogue` при недопустимых
состояниях; встроен в `_execute_decision`). Тесты: `test_interaction.py` (15).

**Критерий готовности:** персонаж выбирает подходящий момент для самостоятельного
взаимодействия.

### Этап 4. Internal State Adapter ✅ (реализован)

**Цель: связать автономное поведение с реальным внутренним состоянием NeuroMita.**

Исследовать существующую систему скуки и эмоций/настроения; подключить их к Motivation;
учитывать индивидуальные особенности персонажа; не создавать дублирующие параметры.
Внутреннее состояние должно влиять на мотивы, а не непосредственно запускать сообщения.

Реализация: `internal_state/adapter.py` — читает реальные `attitude`/`boredom`/
`stress` через `character.get_stats_dict()`, нормализует, добавляет производный
`curiosity`. Кладётся в `perception["internal_state"]` и `engine.stats()`.
Мотивационная связь закрепляется на Этапе 5. Тесты: `test_internal_state.py` (4).

**Критерий готовности:** мотивация отражает внутреннее состояние персонажа.

### Этап 5. Motivation и Decision

**Цель: перейти от простого реагирования к самостоятельному формированию желаний.**

Возможные мотивы: `react_to_event`, `continue_conversation`, `ask_followup`,
`want_to_interact`, `share_thought`, `return_to_unfinished_topic`,
`comment_on_environment`, `perform_activity`. Сначала проверить существующие типы и
избежать дублирования. Motivation определяет, чего персонаж хочет; Decision — стоит ли
реализовывать это сейчас. Decision должен уметь выбрать один из мотивов, отложить или
отказаться от действия, учитывать актуальность, Initiative Gate и предыдущие инициативы,
не создавать повторные ответы.

**Критерий готовности:** персонаж способен самостоятельно сформировать мотив и решить,
когда его реализовать.

### Этап 6. Intention Manager

**Цель: обеспечить непрерывность автономного поведения.**

Задачи: улучшить жизненный цикл намерений; добавить условия выполнения, если их ещё
нет; учитывать сроки актуальности; пересматривать приоритет; отменять устаревшие
намерения; устранять дубликаты; возвращаться к незавершённым темам; восстанавливать
намерения после перезапуска.

**Критерий готовности:** персонаж способен помнить о собственных планах и возвращаться
к ним в подходящий момент.

### Этап 7. Action и Feedback

**Цель: надёжное выполнение самостоятельных действий.**

Задачи: проверить формирование инициативных сообщений; проверить передачу аргументов
инструментам; разделить успешность генерации и доставки; обрабатывать ошибки и отмены;
не считать отсутствие ответа пользователя ошибкой; учитывать реакцию пользователя при
будущих решениях; исключить повторное выполнение действий.

**Критерий готовности:** система понимает, что именно произошло после принятого
решения, и использует результат для дальнейшего поведения.

## 8. Итоговая цель

Initiative Engine должен стать самостоятельным уровнем поведения NeuroMita, а не второй
системой диалога.

Штатная система отвечает на обращения пользователя. Initiative Engine самостоятельно
решает, когда персонажу хочется что-то сделать, сказать или исследовать.

```text
             NeuroMita
                 |
       +---------+---------+
       |                   |
       ▼                   ▼
  Chat System       Initiative Engine
       |                   |
       ▼                   ▼
  Ответ на          Самостоятельные
  сообщение         мотивы и намерения
       |                   |
       ▼                   ▼
  Диалог            Автономные действия
       |                   |
       +---------+---------+
                 |
                 ▼
       Общая память и состояние
```

Обе системы используют общую инфраструктуру NeuroMita, но не должны дублировать
ответственность друг друга.

**Главный критерий успеха: персонаж умеет самостоятельно проявлять инициативу, но при
этом не теряет способность нормально общаться и не начинает разговаривать сам с собой.**

Особенно важно: движку полезно наблюдать за ответами NeuroMita — понимать, что персонаж
уже сказал, какие темы затронул и какие вопросы остались открытыми. Но наблюдение не
должно автоматически порождать ещё один ответ. Именно это разделение позволит получить
автономного персонажа, который продолжает жить и проявлять инициативу самостоятельно,
не ломая уже работающий диалог.
